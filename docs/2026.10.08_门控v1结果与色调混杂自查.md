# 2026.10.08 门控 v1 结果 + 归因自查：色调偏差是一阶混杂（推翻部分既往数字）

> 关联：[免伤门控执行方案（GATE-1）](2026.10.08_免伤门控_执行方案.md)、[A0 公共基准前提判决](2026.10.08_A0公共基准前提判决_结果.md)、[问题清单与解法地图](2026.10.08_问题清单与解法地图.md) 中的 **P5（监督有偏/对齐）**
> 一句话：**门控 v1 的"预登记 PASS"是假的——收益来自"两端误差反相关、混一混就落在 GT 上"；而一个 2 参数的全局色调曲线就能拿到大部分甚至更多的分。P5 从"被低估的隐患"升级为"必须先修的一阶混杂"。**

## 2. 预登记验收结果（表面 PASS）

| 判据 | apr 臂 | apr+clean 臂 | 结论 |
|---|---|---|---|
| **apr**：块级 ΔPSNR（O vs 纯 RDNet）≥ +1.00 dB | **+5.53 dB** | +4.22 dB | 表面 PASS |

> 附：**"干净图负样本"对照臂的裁决** —— 我先前的读数是错的（训练日志里的 g 均值 0.02–0.15 是**批内 80% 干净样本**拉低的，不是门控塌缩）；按集评测：apr 上 g 均值 0.437（与主臂 0.432 相当），但 PSNR 更差（20.80 vs 22.08）、O 相对 I 的 no-harm 更少（6/16 vs 10/16）。
> **结论：干净图负样本不塌缩门控，但确实略微有害 → 主臂不采用。**

## 3. 归因自查：收益是"反射选择"还是"色调对齐"？

**疑点**：apr 上 O=22.08 dB，而两端 I=18.00、P=17.06 —— **两个都不如它，混合却高出 4~5 dB**。只有"两端误差反相关"才可能。

| 探针 | apr | may |
|---|---|---|
| I（原图） | 18.00 | 24.06 |
| P（官方 RDNet） | 17.06 | 22.39 |
| I·β\*（每图最优**标量**增益） | 19.74 | 26.42 |
| **affine(I)（每图最优 2 参数全局色调曲线）** | **20.32** | **26.61** |
| **O（门控）** | **22.08** | **22.42** |
| **O − affine(I)** | **+1.75 dB** | **−4.19 dB** |
| 门控图均值 / 空间 std | 0.432 / 0.362 | 0.533 / 0.388 |

### 判读

1. **一条 2 参数的全局色调曲线就打败官方 RDNet**（apr +3.3 dB、may +4.2 dB）。→ 在我们这块车窗数据上，**主导误差是全局色调/曝光失配，不是反射**。
2. **门控的 +5.02 dB 缩水到 +1.75 dB**（apr），而且在 **may 上比平凡基线差 4.19 dB**。
3. 机理：`β*(I)≈0.86`（I 偏亮）、`β*(P)≈1.15`（P 偏暗）→ **GT 卡在两者中间**，于是"把两端混一混"就落在 GT 上。
4. 根因是**采集协议**：自动曝光下，黑布 GT 与带反射帧的曝光不同（既往已记录"apr I↔GT 增益中位 0.78、暗区 +15.3"、"两侧曝光混杂"）。这就是 **P5**。

## 4. 这个发现推翻了什么（必须回撤/重审的数字）

| 数字 | 现状 | 需重审的原因 |
|---|---|---|
| 门控 v1 "apr +5.53 dB" | **作废** | 归因后仅 +1.75 dB 高于平凡色调基线，且 may 上为负 |
| E4 "oracle 门控 +2.02 dB" | **待重审** | 其 oracle 是逐块在 {I, P} 间取优——在色调偏差下，"选更暗的那个"本身就是色调修正 |
| E3 "干净区 −2.26 dB、72% 块为负" | **待重审** | ΔPSNR 用原始像素计算，未做光度归一化 |
| E3 "亮反射 +4.84 dB" | **待重审** | 同上（可能部分来自"官方把亮区压暗正好对上偏暗的 GT"） |
| 9.22 "官方全图色调压暗 −12~−31" | **部分成立** | 该结论本来就是"官方行为≈色调压暗"，与本发现一致，反而互为佐证 |
| S2/LOVO 系列（判据 ①–⑤、③⑦） | **需确认口径** | 若判据基于增益对齐后的量（ρ、med_ratio 多为比值型），受影响较小；纯 PSNR 类需重算 |

## 5. 纪律教训（写进护栏）

1. **平凡基线必须含"每图一条全局色调曲线"（affine）+ 标量增益**——我们自己的护栏本就写着"评测面板必带常数/平凡基线"，这次门控验收**漏了**，才让假 PASS 走到报数这一步；
2. **凡在 apr/may 上做 PSNR 类结论，必须做光度归一化**（协议 v2 的"锁 AE/AF"正是为此）；
3. 门控/任何方法在车窗数据上的净收益，**只能相对"色调归一化后的输入"来报**，不能相对原始输入。
