## 2. apr 选帧扫描 —— **判决「救不回」**（待办 1 结项）

**依据**：6 场景 / 359 帧全扫，三条独立口径同向。

| 口径 | 脚本 | 结果 |
|---|---|---|
| 逐帧光度轨迹（**无循环**，主判据） | `scripts/step_apr_1012.py` | 段内含 **2–9 处 ≥5% 阶跃**，最大单步 **29%** |
| 与现行 GT 的光度等价类 | `scripts/direct_apr_gt_1012.py` | 等价帧仅 6–46 帧，**全部落在 GT 之前** |
| 与输入 I 的光度一致性 | `scripts/verdict_apr_gt_1012.py` | 现行 GT 落在一致窗口内 **1/6**，其余 5 个在窗外 |

**根因**：偏移是**跨段**的（反射段 帧0–600 ↔ 布段末段 帧350–1100），两个集合**不相交**。段内换帧改不了段间关系；这正是"布合上改变透射照明"的又一次体现——**问题在采集侧，不在选帧**。

### ⚠️ 需更正交接页 §4 的一句判断

> 交接页原文："apr 的 GT 在漂移末端，与六月'瞬时跳变'机制不同"

**实测不成立**：apr 同样是**跨段**偏移，段内只是叠加了几次 5–29% 的阶跃（更像手机 AE 分档/重新收敛，而非连续追赶）。结论与六月一致：**偏移在"布合上"前后即完整存在**。

### ⚠️ 三处数据记载需更正

| 项 | 交接页/README | 实测 |
|---|---|---|
| GT = 视频末帧 | 6 个场景都如此（875/400/475/625/725/1025） | **只有 3 个**：172719(875)、173349(625)、173604(725)。172933 的 GT=400 而目录到 575、173237=475/600、173827=1025/1200 |
| README 的 `total_frames` | 64/52/53/54/59/77 | ✅ 一致，但那是**目录内帧文件数**，不是原始帧数；帧号跨度是 0–875 / 0–400 / … / 0–1025 |

### 方法学教训（**新增，写给自己**）

本项前后写了 4 版脚本，**前 3 版的"最优帧"都是构造性伪影**：

| 版本 | 循环在哪 | 后果 |
|---|---|---|
| `scan_apr_gt_1012.py` | 锚点=第一张 I 帧 | `g(anchor,anchor)≡1` → 6/6 场景"最优帧"都是 I 帧本身，还给出"5/6 有实质改善"的**假结论** |
| `verdict_apr_gt_1012.py` | 锚点=I 帧均值 | 自比消失，但答不了"能否换帧" |
| `direct_apr_gt_1012.py` | 锚点=现行 GT.png | `g(GT,GT)≡1` → "最优帧"必为 GT 自己 |
| `step_apr_1012.py` | 锚点=首帧，不用 GT/I 信息 | ✅ 无循环 |

> **把"候选"和"参考"放进同一个集合、再按相似度排序，参考必然夺冠。**
> 这是交接页 §11 教训 2（"不设平凡基线的探针会给出想要的错误答案"）的同族新条目。

### 4.3 ⚠️ LightRR 有一个真实尺寸 Bug（**下次上自己数据前必读**）

**`IDWT_2D` 在任一维为奇数时静默丢一行/一列**：
```
idwt((1,256,48,67)) -> (1,256,96,134)      # 67 -> 134
```
→ 触发 `AFM_LowFrequencySSM` 的 `assert yw == W`。**要求 H、W 都是 32 的倍数。**

**本课题数据几乎全部违反**：real20 1114×717、SIR2 540×400、自采 955×934 / 1427×859 / 1018×671…

**解法（已实现并验证）**：`scripts/lightrr_infer.py` 的 `LightRRInfer`
—— **pad 到 32 的倍数 → 推理 → 裁回原尺寸**。12 尺寸实测 11 通过
（唯一失败是 1080×1920 OOM，与尺寸合法性无关）。
比官方 `--if_align`（直接 resize 裁掉像素）更干净，且输出尺寸恒等于输入，
可与 RDNet 逐像素对齐比较。

**另一条硬限制**：`CrossChannelAtt` 是**全局注意力** `O((H·W)²)`。
real20 原生 1114×717 需 **约 25 GB** → 这就是论文给 real20 单设 `real20_420` 的原因。
**本课题大尺寸自采数据必须先降到长边 ~420–540。**

### 4.4 一条备选路（已验证可行）

本仓 `ExpoMamba/models/selective_scan_triton.py` 是**同签名 Triton 实现**，
其声明布局与 LightRR 的调用逐项一致。**mamba 编译不是必经之路**——

## 7. 成本教训（本会话新增）

1. **"偶然成功"不等于"正确路径"**。LightRR 的 mamba 扩展第一次编译"成功"，只是恰好把 GitHub 上的预编译 wheel 下下来了；我清掉缓存后才暴露"`github.com` 不通 → 下载必然失败"的真相。**任何一次成功都要问：它为什么成功？换个环境还成立吗？**
2. **一个任务卡 >20 分钟就该换思路**。用户提醒得对：mamba 编译卡了两次共约 40 分钟，而本仓 `ExpoMamba` 里早就躺着现成的 Triton 替代实现。**先搜本仓有没有现成解**，再考虑硬啃编译。
3. **构建类任务要在开始前把"依赖地图"一次问清**：本次 7 个坑里，坑 4/5/6（GitHub 不通、sdist 缺 csrc、conda 不装 CUDA 头库）任何一个都足以让整条路失败，却都在踩到之后才发现。
4. **Shared 机器上构建要钉卡**：构建期 CUDA 初始化遇忙卡会假死 7 分钟，加 `CUDA_VISIBLE_DEVICES` 即解。
5. **把参考放进候选集 = 构造性伪影**（见 §2 方法学教训）。
6. **远端长任务一律 `nohup ... < /dev/null &`**，且**别在同一个 `exec` 里串两次构建**——本次 `install_cuda_libs.sh` 用 `exec bash build_final.sh` 重启构建时，前一版的 `timeout` 包装进程把新构建杀了一次（exit 137），白等 5 分钟。
